# 《资料库》配套手机 App —— 需求文档（v1.0）

> **给实现者（AI/开发者）的话**：本文档自包含，读完即可开工。所有协议帧格式与手环快应用侧**已实现的代码精确对齐**（手环侧代码索引见 §8），照此实现即可直接联调，不需要再猜格式。
>
> **一句话需求**：做一个 Android 手机 App，让用户把「资料集文件」通过蓝牙互联通道传给小米手环 9 上的快应用《资料库》；手环收到后自动进入加载页建立索引缓存，随后即可被搜索到。可选的二期能力：语音搜索的 ASR 对端、AI 搜索的云端应答对端。

---

## 1. 背景与运行环境

| 项 | 说明 |
|---|---|
| 手环端 | 小米手环 9，Vela 快应用《资料库》（velaPro 工程） |
| 手环端接收实现 | 已实现并进包（v1.16.46）：`src/SearchEngine/BtTransfer.js` |
| 手机端 App | **本需求文档的实现对象**（Android，Demo 级别即可） |
| 通信通道 | 快应用 `@system.interconnect`（官方互联通道）—— 手机 App 是它的对端 |

**通道技术选型（务必先读，这是 Demo 最大风险点）**：

快应用的 `@system.interconnect` 官方定义是「手表快应用 ⟷ 手机端互联 App」的消息通道。手机侧要成为对端，正统路线是**接入小米穿戴互联能力（xms-wearable 互联 SDK / 小米运动健康 App 的互联服务）**：

- **路线 A（正统，推荐）**：集成互联 SDK，创建 interconnect 会话后即可收发下文 §3 的 JSON 帧。需要申请 SDK 权限（小米开放平台 / 穿戴应用开发者资质）。
- **路线 B（Demo 兜底，无 SDK 时）**：先实现**完整的 UI + 文件管理 + 协议编码**（把帧格式用 mock transport 自测通过），把「物理发送」抽象为一个 `Transport` 接口；拿到 SDK 后只替换 Transport 实现。本文档按这个结构写，两个路线共用 95% 代码。
- ⚠️ 不要尝试 BLE 直连手环系统或 SPP 私有协议来"注入"快应用消息——那是系统级通道（本项目 ble_tools 已打通，用于装 rpk），**没有向快应用转发 interconnect 消息的语义**，不可行。

## 2. 功能需求（Demo 范围）

### 2.1 必须做（P0）

1. **资料集管理**：App 内置 1~2 个示例资料集（文件放 assets/，见 §5 造法）；列表展示（名称/条数/文件大小）。
2. **发送资料集**：点「发送到手环」→ 按 §3.1 协议逐帧下发（显示分片进度百分比）。
3. **连接状态与结果反馈**：显示「等待手环 / 传输中 / 传输完成（手环正在建立缓存）/ 失败（可重试）」。
4. **连接保持**：传输期间保持互联会话存活；手环侧断开重连后能重发（幂等，见 §4.3）。

### 2.2 可选（P1，二期）

5. **语音搜索对端**：收到手环 `{type:'voice_search'}` → 调 ASR（可先用手机系统语音识别 / 云端 ASR）→ 回 `{type:'voice_result', text}`。当前 Demo 可先回固定测试词。
6. **AI 搜索对端**：收到 `{type:'ai_search', q}` → 调云端大模型生成回答 → 回 `{type:'ai_result', answer, results}`。当前 Demo 可先回模板文案。

## 3. 通信协议（★ 实现契约，逐字节对齐手环侧）

**统一载体**：interconnect 文本消息。手环侧发送为 `conn.send({data: '<JSON 字符串>'})`，接收为 `onmessage(data)` 且**取 `data.data` 字段再 `JSON.parse`**。手机侧同理：发送 JSON 字符串，接收后解析 `data.data`。

### 3.1 资料集传输协议（四类帧）

```jsonc
// ① 传输开始（一次传输的声明）
{ "t": "ds-begin", "ds": "english_plus", "name": "英语扩展", "total": 3 }

// ② 分片数据（大文件切成多帧；小文件也可直接用 ③）
//    ds=集目录名  f=文件名  i=分片序号(从0起)  last=是否该文件最后一帧  data=文本片段
{ "t": "ds-chunk", "ds": "english_plus", "f": "map_0.txt", "i": 0, "last": 0, "data": "…前 4KB…" }
{ "t": "ds-chunk", "ds": "english_plus", "f": "map_0.txt", "i": 1, "last": 1, "data": "…剩余…" }

// ③ 单帧整文件（文件小于单帧上限时可用，等价于只有一个 i=0,last=1 的 chunk）
{ "t": "ds-file", "ds": "english_plus", "f": "meta.txt", "data": "…整个文件内容…" }

// ④ 传输结束（手环收到后校验文件齐 → 落盘沙箱 → 注册资料集 → 自动进加载页建缓存）
{ "t": "ds-end", "ds": "english_plus" }
```

**规则**：
- `ds` 是集目录名：`^[a-z0-9_]{2,32}$`（小写字母/数字/下划线，避免与内置集冲突建议加后缀）。
- 帧序：`ds-begin` → 若干 `ds-chunk`/`ds-file`（文件任意顺序，手环按文件名+序号拼装）→ `ds-end`。
- **单帧 data 建议 ≤ 4KB**（interconnect 消息上限未知，取保守值；UTF-8 文本按字节算，中文 3 字节/字）。
- 手环侧**逐文件整体校验后一次性写盘**：文件名必须与内容相匹配（见 §5 文件清单），`meta.txt` 必须存在否则加载会失败。
- 重复传输同一 `ds` 名：手环侧**幂等**（重新注册返回已有项，缓存按数据版本自动重建）——断线重发整个流程即可，无需清理。

### 3.2 语音搜索对端协议（P1）

```
手环 → 手机： { "type": "voice_search" }
手机 → 手环： { "type": "voice_result", "text": "识别出的搜索词" }
```

### 3.3 AI 搜索对端协议（P1）

```
手环 → 手机： { "type": "ai_search", "q": "手环用户输入的问题" }
手机 → 手环： { "type": "ai_result", "answer": "回答文案（300字内）", "results": [ ... ] }
```
- `results` 可选（≤5 条来源条目），每条字段与手环搜索结果卡一致：
  `{ "id": <手环内条目ID，未知填0>, "title": "标题", "region": "分类名" }`
- 手环侧超时兜底：长时间无响应会自动降级本地模拟回答（不影响 Demo 观感）。

### 3.4 Transport 抽象（路线 B 的关键设计）

```kotlin
interface HandBandTransport {
    fun connect(onState: (connected: Boolean) -> Unit)
    fun send(jsonFrame: String)          // §3 的 JSON 字符串
    var onMessage: ((String) -> Unit)?   // 收到手环消息（JSON 字符串）
}
```
实现 A（SDK）与实现 B（mock：日志打印 + 本地回环自测）互换，上层 UI/业务不变。

## 4. App 侧交互流程（P0）

```
[资料集列表] --点选--> [资料集详情(名称/条数/估算文件大小)]
      --「发送到手环」--> 检测连接
            ├─ 未连接：提示「请保持手环与手机互联」+ 重试按钮
            └─ 已连接：进入传输页
                  ├─ 发送 ds-begin(total=N)
                  ├─ 按文件顺序：读文件 → 切分片 → 逐帧 ds-chunk（进度条 = 已发字节/总字节）
                  ├─ 发送 ds-end
                  ├─ 显示「传输完成，手环正在建立索引」
                  └─ 3~5 秒后显示「完成」，提示用户在手环上查看《资料库》
```

### 4.3 失败与重试
- 任一帧发送失败：累计重试 3 次（间隔 1s），仍失败 → 展示错误 + 「重新发送」按钮（从头重发整个流程，手环幂等）。
- 传输中 App 切后台：Demo 允许中断（回前台提示重发）；正式版建议前台服务保活。

## 5. 资料集文件从哪来（App 要发送的内容）

一个资料集 = 一个目录，含以下文件（详细格式见 velaPro 的 `docs/资料拆分指南.md`）：

| 文件 | 内容 | 必需 |
|---|---|---|
| `meta.txt` | 引擎元数据（单行 JSON：totalCount/regionList/maps/mapChunkSize 等） | ✅ |
| `map_N.txt` | 目录条目分片（`localId\|year\|regionIdx\|标题` 行） | ✅ |
| `detail_N.txt` | 详情分片（`localId\|关键词\|字段1\|字段2…` 行） | ✅ |
| `block_0.txt` | 搜索倒排桶（`桶号\|id,id,…` 行） | ✅ |
| `meta.json` | 人类可读声明（引擎不读，可省略） | ⭕ |
| `icon.png` | 集图标（可选，Demo 可省略） | ⭕ |

**造测试集（最快路径，在电脑上执行）**：
```bash
cd velaPro
# 用现成工具拆一个集（示例：英语集→输出到 dist 目录查看文件）
node tools/split_dataset.js english --out /tmp/demo_ds/english
ls /tmp/demo_ds/english   # meta.txt map_0.txt detail_0.txt block_0.txt …
```
把 `meta.txt` + `map_*.txt` + `detail_*.txt` + `block_0.txt` 放进 App 的 `assets/datasets/english/` 即可。**建议 Demo 用一个小集**（条数 ≤200，总大小 <200KB，分片帧数少传输快）；也可以手写一个 10 条的迷你集测试。

**内置集的参考体积**（供选型，实测）：英语 750 条约 65KB、诗词 550 条约 509KB、健康 1000 条约 377KB。

## 6. 验收标准（端到端）

| # | 操作 | 预期现象（手环端） |
|---|---|---|
| 1 | App 发送资料集（全部帧成功） | 手环**自动跳转到加载页**，进度文案「加载蓝牙资料…」→「读取资料元数据」→「建立检索索引」→「完成」，随后回首页 |
| 2 | 手环首页搜索该集的内容词 | 能搜到新资料集的条目，点开详情正常 |
| 3 | 重发同一资料集 | 手环重复加载一次（幂等），搜索无重复条目异常 |
| 4 | 传输中途断开 | 手环无异常（不会卡加载页）；App 重发后走验收 1 |

**手环侧日志对照**（联调时看手环 console）：应出现
`[蓝牙资料] 开始接收资料集: xxx（N 个文件）` → `[蓝牙资料] 接收完成…落盘中…` → `[蓝牙资料] 落盘完成: internal://files/datasets/xxx/` → `[DM] 动态资料集已注册: id=100 …`。

## 7. 工程建议（极速 Demo）

- **技术栈**：Android 原生 **Kotlin + 协程 + ViewBinding**（单 Activity + 2~3 个 Fragment/Compose 页即可）；最低 SDK 26。
- **零第三方依赖**即可完成 P0（JSON 用 org.json，文件走 assets）。
- **代码结构建议**：
  ```
  transport/HandBandTransport.kt   // §3.4 接口 + SdkTransport / MockTransport
  protocol/DsProtocol.kt           // 帧编码（§3.1/3.2/3.3）+ 分片器（4KB 切分）
  data/Dataset.kt                  // 资料集扫描（assets 目录列举）+ 文件读取
  ui/MainActivity.kt               // 列表 + 详情 + 传输页 + 进度
  ```
- **自测（无手环也能做）**：MockTransport 把发出的每一帧写日志，用 §3.1 的规则写一个"回放校验"（帧序/字段/分片重组 == 原始文件）即视为 P0 完成。
- **联调顺序**：先发迷你集（1 个 10 条集）打通全链路，再发大集调分片节奏（帧间隔建议 50~100ms，避免消息通道拥塞）。

## AI 问答蓝牙协议（ai_chat，v1.16.90 新增）

配合手环端「AI 助手」专属界面（两页式：提问页 → 回答页）。**拒绝流式输出**——手机端必须等大模型回答完毕后一次性回包，手环端不做分片拼接。

### 请求（手环 → 手机）

```json
{ "type": "ai_chat", "qid": 1, "question": "感冒了怎么办" }
```

- `qid`：自增序号，每发起一次请求 +1；手机端应答必须原样带回。
- `question`：用户问题原文。

### 应答（手机 → 手环）

```json
{
  "type": "ai_chat_result",
  "qid": 1,
  "ok": true,
  "answer": "<完整回答文本（纯文本兜底/概要）>",
  "card": {
    "summary": "<一句话结论>",
    "sections": [
      { "name": "<小节名，如 操作步骤 / 注意事项 / 概况>", "items": ["<要点 1>", "<要点 2>"] }
    ],
    "note": "<尾注（如免责声明）>"
  },
  "sources": [
    { "title": "<条目名>", "gid": 123456 }
  ]
}
```

**结构化作答卡（card，v1.16.101 起，强烈建议提供）**：手环回答页按「结论段 → 分节卡 → 尾注」渲染（仿词条详情页分节视觉），比大段纯文本更清晰规范。填写约定：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `card.summary` | 是（提供 card 时） | 一句话结论，展示在「AI 回答」卡首行 |
| `card.sections` | 否 | 0~4 个小节；每节 `name` 为小节名（建议 4 字内，如"操作步骤""注意事项"），`items` 为要点短句数组（建议 2~5 条、单条 40 字内） |
| `card.note` | 否 | 尾注，如「以上内容由 AI 生成，仅供参考」等免责声明 |
| `answer` | 是 | 纯文本兜底：未提供 `card` 时直接渲染；提供 `card` 时作为概要兼降级备份 |

**不同问题类型的建议小节结构**（供手机端 AI 参考）：
- 方法/操作类（"怎么急救""如何改善睡眠"）→ sections: 操作步骤 / 注意事项
- 知识介绍类（"唐朝是什么"）→ sections: 概况 / 影响或延伸
- 对比选择类（"A 和 B 哪个好"）→ sections: 共同点 / 差异 / 建议
- 需要就医/风险类 → 单独一节「需要及时就医」等警示小节 + note 免责声明

- `qid` 不等于当前挂起序号的应答会被手环端直接丢弃（防旧答案污染新问题）。
- `ok: false` 表示手机端处理失败，手环端降级本地回答。
- **回答生成口径（重要）**：`answer` 由**手机端大模型**生成——依据**模型自身知识**或**联网搜索**作答，**不依赖手环本地资料库**（AI 搜索的定位是"搜集更多资料、更权威、覆盖面更大"，与手环内的离线资料检索相互独立）。
- `sources`：**可选**。联网来源仅提供 `title` 即可（手环端仅展示、不可点击）；若引用手环本地条目，带 `gid`（跨集全局条目 id）时手环端点击可进词条详情。无来源时省略或传空数组。
- 手环端超时 12s：无应答自动降级——模拟器/演示环境返回预置的通用知识回答（覆盖感冒、急救、睡眠等常见问题），保证功能不中断。
