## 一、需求背景

需求原文（2026-10-10）：

> 主界面资料图标滑动设计就给他删掉，到时候在手机应用可以像更改手环组件一样自定义主界面显示哪些资料图标，既可以让 UI 布局不那么复杂，也可以一定程度上增加个性。

拆解为两件事：

| # | 事项 | 端 | 状态 |
|---|------|----|------|
| 1 | 删除主界面资料图标**横滑设计**（scroll-x + 吸附），改为更简单的固定布局 | 手环端 | 布局方案见 §5，待确认后排布细节 |
| 2 | **手机 App 自定义**主界面显示哪些资料图标（选择、排序），经蓝牙下发给手环 | 手机端 + 手环端 | 本文定义协议与架构 |

价值：主界面布局更简单（少一条横滑手势与吸附状态机）+ 个性化（用户挑选自己的首页图标，类似换表盘组件的心智）。

## 二、现有蓝牙链路（必读）

### 2.1 通道

手环端快应用与手机 App 之间使用 Vela 官方互联层 **`@system.interconnect`**：

```js
// 手环端（已封装好，勿另起通道）
var interconnect = require('@system.interconnect')
var conn = interconnect.instance()
conn.send({ data: JSON.stringify(obj) })   // 手环 → 手机
conn.onmessage = function (data) {...}     // 手机 → 手环（data 可能是 {data:'<json串>'} 包装或裸串，接收端已双兼容）
conn.getReadyState({ success: function(d){ d.status === 1 即已连接 } })
```

手机侧对应 **小米 xms-wearable SDK**（参考 `小米穿戴第三方app能力开发demo_1.4/`）。⚠️ 通信前两端签名/证书需一致（官方 FAQ 约束）。

⚠️ **注意与 ble_tools SPP 直连的区别**：项目里另有一条自研 SPP（RFCOMM ch5 + authKey 认证，见 `ble_tools/`、`xiaomi-band9-mcp/`）用于**装/卸 rpk**，它与 interconnect 是**两条独立链路**。配置下发**必须走 interconnect**，不要走 SPP。

### 2.2 现有协议帧（同一条 onmessage 上复用）

| 帧 | 方向 | 载荷要点 | 路由模块 |
|---|---|---|---|
| `ds-begin / ds-chunk / ds-file / ds-abort / ds-end` | 手机→手环 | 资料集文件传输（`t` 字段路由） | `SearchEngine/BtTransfer.js` |
| `voice_search`、`ai_search`、`ai_chat` | 手环→手机 | 语音/AI 请求（`type` 字段路由） | `SearchEngine/AssistantEngine.js` |
| `voice_result`、`ai_chat_result` | 手机→手环 | 语音识别文本 / AI 回答 | AssistantEngine |

**两条接收约定（手环端已实现，手机端只需遵守）**：

1. **onmessage 包装链**：BtTransfer 与 AssistantEngine 共用一条 `conn.onmessage`，采用"保留前一个 handler 并转发"的包装链，任何一端先设后设都不互相覆盖。手机端**不需要关心**，但意味着**所有帧都会广播给所有模块** —— 每个模块只处理自己 `t`/`type` 前缀的帧，其余静默忽略。
2. **JSON 双形态**：投递可能是 `{data:'<json串>'}` 包装或裸字符串/对象，手环端统一兜住。手机端发送时统一用 `send({ data: JSON.stringify(frame) })`。

### 2.3 关键源文件（手环端）

| 文件 | 作用 |
|---|---|
| `src/SearchEngine/BtTransfer.js` | 应用级接收器（ds-* 协议 + 落盘 + 注册），**cfg-* 协议在此扩展** |
| `src/SearchEngine/AssistantEngine.js` | 语音/AI 链路（type 协议），头部长注释即协议文档 |
| `src/app.ux` | onCreate 里 `initBtReceiver()` 启动全局监听 |
| `src/pages/btransfer/btransfer.ux` | 传输进度 UI（读 `getTransferState()` 轮询） |
| `src/pages/index/index.ux` | 主界面（图标行 `cat-scroll`，将改造为配置驱动） |

## 三、新协议设计：主界面图标配置（cfg-home 族）

### 3.1 设计原则

- 复用 interconnect 同一通道、同一 onmessage 包装链；帧用 **`t` 字段**路由（与 ds-* 同族，均为"配置/传输类"，与 AssistantEngine 的 `type` 族区分）。
- 配置体很小（< 1KB），**单帧携带、不分片**（区别于 ds-* 的分片传输）。
- 每一步手机→手环的操作，手环都回 **ack 帧**（手环→手机），手机端可据此提示成功/失败。
- 配置带 `ver` 自增版本号，便于去重与展示"上次修改时间"。

### 3.2 帧定义

#### ① 拉取手环端现状（手机端进入自定义页时调用）

```json
// 手机 → 手环
{ "t": "cfg-query" }

// 手环 → 手机（回执）
{ "t": "cfg-state", "ok": true,
  "cur": { "ver": 3, "icons": [ {"ds":"history","name":"历史","icon":"history","color":"orange"} ] },
  "installed": [ {"ds":"history","name":"历史","count":850},
                 {"ds":"poems","name":"诗词","count":10000} ],
  "capacity": { "pill": 2, "rect": 4, "max": 6 } }
```

- `cur`：当前生效配置；**无自定义配置时 `cur` 为 `null`**（表示用默认布局）。
- `installed`：手环已安装的全部资料集（内置 + 蓝牙接收的），`count` 为条数。这是手机端可选图标的数据源。
- `capacity`：手环端容量 —— `pill`/`rect` 为各形态一行可见的固定槽位数（胶囊 2、方屏 4，与原横滑初始可见数一致），`max` 为配置总上限。**icons 顺序即优先级**：手环只显示前 capacity 个，手机端 UI 应提示「排在越前越常显示」。

#### ② 下发新配置

```json
// 手机 → 手环
{ "t": "cfg-home", "ver": 4,
  "icons": [ {"ds":"poems","name":"诗词","icon":"poems","color":"blue"},
             {"ds":"history","name":"历史","icon":"history","color":"orange"} ] }
```

- `ver`：手机端在 `cfg-state.cur.ver` 基础上 +1（无配置则从 1 起）。手环校验 ver 必须大于当前值，否则拒绝（防旧包乱序）。
- `icons`：**有序数组 = 主界面从左到右/从上到下的显示顺序**。空数组 = 清空自定义、恢复默认布局。
- 每项字段（**v1.16.253 定稿：只需 `ds`**）：
  - `ds`：入口标识（必须 ∈ `installed[].ds`，手环端校验，不合法则整包拒绝）
  - `name/icon/color`：手机端可不传 —— 手环渲染一律用本机 entry 自身的名称/图标/配色（防两端不一致）；传了也会被忽略。

#### ③ 手环回执（两种结果）

```json
// 成功
{ "t": "cfg-ack", "ok": true, "ver": 4 }
// 失败（err 为机器可读码 + 中文说明，手机端直接展示）
{ "t": "cfg-ack", "ok": false, "ver": 4,
  "err": "BAD_DS | 未知资料集: history2" }
```

错误码枚举：`BAD_JSON`（帧解析失败）、`BAD_VER`（版本号不递增）、`BAD_DS`（含未安装资料集）、`TOO_MANY`（超过 maxIcons）、`BAD_FIELD`（字段类型/取值非法）、`STORE_FAIL`（storage 写入失败）。

#### ④ 恢复默认（等价于下发空 icons，手机端也可显式调用）

```json
// 手机 → 手环
{ "t": "cfg-home", "ver": 5, "icons": [] }
// 手环 → 手机
{ "t": "cfg-ack", "ok": true, "ver": 5 }
```

### 3.3 图标（icon 字段）规范

手环端内置一组图标 PNG（rpk 内 `/common/icons/cat_<name>.png`，现有 6 类：history/poems/english/health/life/study 等，以手环端 `cfg-state.installed[].icon` 返回的为准）。

- 手机端选择图标时**直接引用 `cfg-query` 返回的建议值**，不要自造名字 —— 手环端对未知 icon 名回退为通用书本图标（不报错，但显示兜底）。
- **图片自定义（手机上传 PNG）一期不做**：interconnect 传图 + 手环沙箱存图 + 图标缓存管理成本高；`icon` 字段已预留字符串空间，二期可扩展为 `file:<沙箱路径>`。

## 四、手环端存储与生效逻辑（手环端 AI 实现，此处为接口约定）

- storage key：`home_icon_config`，值为 JSON 字符串：`{"ver":4,"icons":[...]}`
- 启动流程：index 页 onInit 读 storage → 解析校验（失败/无 → 默认布局）→ 渲染
- 生效时机：收到 `cfg-home` 写 storage 成功后，若主界面在前台**立即刷新**（global 脏标志 `homeIconDirty` + index 轮询/onShow 刷新）；否则下次回主页生效。
- 默认布局定义：无配置时沿用现状逻辑（分组 groupEntries 优先，回退 datasetEntries），**该行为不变**。

## 五、手环端布局改造（✅ 已实施，1.16.252/253，定案版）

**用户定案（2026-10-11）**：手环 UI 基本不变，图标位置跟现在基本一样，但不能左右滑动 —— 固定槽位，显示哪些/顺序由手机自定义。

### 5.1 已实施改动（index.ux）

- 模板：`cat-scroll` **保留 scroll 组件**（布局行为与旧版一致），改 `scroll-x="{{false}}"` 禁横滑，删除 `onscroll` 绑定与 `id`；
  渲染列表 `displayCats` → **`visibleCats`**（computed 按形态取前 N：胶囊 2 / 方屏 4）。
- JS 删除横滑吸附状态机：`onCatScroll / snapCatScroll / _catTargetX / snapParams / catScrollTimer / _lastCatScrollX / _catIdx`。
- 新增图标配置应用：`_applyIconConfig()`（global.homeIconCfg 优先，按 ds 映射入口，无效跳过，全无效回默认）；
  onShow 消费 `homeIconDirty` 脏标志；注册 `global._homeIconRefresher` 供 cfg-home 生效后**前台即时刷新**；onDestroy 注销。
- ⚠️ 实施教训：252 曾把 scroll 开标签改 div 而闭合仍是 `</scroll>`（标签错配）→ 图标被横向压缩裁切、双屏布局塌陷 —— **本运行时模板标签错配不报错但渲染错乱**，改容器标签必须开闭同步。

### 5.2 最终布局

- 胶囊屏：一行 2 个 95px 图标（位置 = 原横滑初始态）；方屏：一行 4 个 58px 图标。
- 超出容量的配置项不显示（手环取前 N）；点击 → 原 `goCategory` 逻辑不变。
- 搜索态/语音态隐藏逻辑不变（catScrollMT 动态 margin 保留）。

### 5.3 模拟器验证（1.16.253 实测截图）

- 胶囊屏（Vela_band9）：2 图标完整、位置与像素级校验一致（95 设计宽 ✓）；图标行水平 swipe 后图标位置不变（横滑禁用 ✓）。
- 方屏（Vel-pro）：4 图标一行完整；swipe 命中图标直接进入资料页（进一步证明不滚动）✓；资料页渲染正常。

## 六、手机端（蓝牙 AI）实现清单

1. **通道**：xms-wearable SDK 数据通道（与现有 demo 一致），发送 `send({data: JSON.stringify(frame)})` 形态的等价物；接收手环帧按 `t`/`type` 分发。
2. **自定义页 UI**：
   - 进页 → 发 `cfg-query` → 用 `cfg-state` 渲染：当前布局（cur）+ 可选列表（installed）+ 上限（maxIcons）
   - 编辑：勾选/取消、上下排序；数量 > maxIcons 禁止下发
   - 保存 → 发 `cfg-home` → 等 `cfg-ack`（**建议 5s 超时**，超时提示"手环无响应，请确认手环亮屏且 App 在前台"）
3. **帧规则**：只认 `t` 前缀 `cfg-` 的帧；**忽略** `ds-*` 与 `type` 帧（它们是别的模块的）。
4. **重连与幂等**：下发失败可重发（ver 不变也可，手环只拒绝 ver ≤ 当前值的**旧**配置 —— 注意重发同一 ver 会被拒，重试前先 `cfg-query` 拉最新）。
5. **签名/证书**：与既有 demo 相同配置（两端一致），否则 interconnect 不通。

## 七、边界与容错（两端共同遵守）

| 场景 | 行为 |
|---|---|
| 配置里的集被卸载（蓝牙集被删/出厂） | 手环端渲染时跳过该图标（storage 不动），下次 cfg-query 的 installed 不含它 |
| icons 为空数组 | 恢复默认布局（等同无配置），cur 返回 null 或 ver 保留均可 |
| JSON 解析失败 / 字段缺失 | 整包拒绝，回 `cfg-ack ok:false`，手环端保持原配置不变 |
| 手环 storage 满/写失败 | 回 `STORE_FAIL`，原配置保留 |
| 传输中手环切后台 | storage 写入不依赖前台；UI 刷新依赖 onShow，回主页自然生效 |

## 八、联调计划（建议顺序）

1. **手环端先行**：实现 cfg-* 接收 + storage + 主界面网格渲染（含默认布局回归）。
2. **模拟联调**：手环端在 AssistantEngine 同款位置加"模拟对端"开关（无手机时用本地脚本注入 cfg 帧调 handleMessage），验证状态机。
3. **真机联调**：手机 demo App 先手工发帧（一个按钮发固定 JSON）→ 再做完整自定义 UI。
4. **验收**：手机改布局 → 手环主界面即时变化；卸载集后图标自动消失；恢复默认。
